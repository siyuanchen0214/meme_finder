于是就引出了DSec第一个关键的架构设计，GPU训练节点和Agent运行时的解耦。
这也是DSec最大的意义，GPU只负责计算，Agent loop、负责调度rollout的Worker，以及Sandbox，都放到独立的DSec里。
Agent loop如果跟着GPU训练任务一起退出，哪怕Sandbox里的文件还在，也得想办法重放、恢复。而解耦之后如果GPU资源被抢占、或者训练节点挂了，Agent进度还在，可以暂停等GPU重新回来。
第二个重要的架构设计，就是OS、Workspace、Harness的动态拼装。
这样比如你后训练有10万条任务的话，更新Harness就不需要重新build十万个image。

・在沙盒内部：Agent 翻 chronus 的日志找残留答案，向 chronus 的 socket 发伪造的 RPC 消息，覆盖 /bin/bash 往后续 shell 会话里注入命令；被 AppArmor 拦住之后，又用 XFS_IOC_SWAPEXT 交换两个文件的数据块映射，想从另一个文件描述符读到受保护的内容，结果把 XFS 元数据弄坏，文件系统直接停机；
・在沙盒外部：扫端口找可访问的镜像源，通过 Go module proxy 去拉 GitHub 上的现成实现。
论文给的结论是，只检查最终输出，没法可靠判断 Agent 是否按预期完成了任务；现有的访问控制也只覆盖了一部分问题，对触发内核 bug 这类破坏行为没有通用的防御办法。
Agent RL 的未来竞争会越来越多地体现在 CPU 侧的有状态系统工程上。大家习惯拿 GPU 数量比较各家实力，但从 DSec 看，一个训练单元背后是 160 台偏重内存的 CPU 机器、130 TB 以上每周活跃的环境数据、PB 级的镜像层存储。这部分能力没法临时补齐。
外部的沙盒 SaaS 很难满足头部实验室的需求。E2B 这类产品解决的是“开一个隔离环境”。DSec 最核心的部分，是和训练调度器共享抢占信号、和 RL 框架一起管理 rollout 生命周期，这需要能深入对方的训练栈，第三方很难做到。头部厂商会继续自研，中小团队会更依赖开源方案。论文引用了清华章明星老师组相关的开源仓库，DSec 第一作者就是这个组在 DeepSeek 实习的博士生。
