第 3 节的事件驱动设计让 Agent 能够被更广泛的环境驱动，但也增加了接触不可信输入的风险。如果没有办法很好的解决安全与隐私问题，那么 Super-agent 只有在一个很小且可信的范围才能工作。
例如，第 5 节将 Agent Loop 部署在云端、并在各类执行设备上安装轻量 daemon，这一设计默认建立在云端与端侧环境彼此受信任的前提之上。但当云端的 Agent Loop 持续接入外部环境事件、而端侧设备上又存有私有代码、敏感数据与本地凭据时，这种跨设备连接便引入了显著的安全与隐私隐患。一旦云端的 Agent Loop 遭遇服务端入侵或提示词注入而被攻破，其连接的全部端侧设备都面临被控制的潜在风险。
此外，即使云端未被攻破，只要端侧环境中的凭据能够进入模型的上下文，正常执行过程中同样存在凭据泄露的风险；因此还需要设计相应的机制，让 Agent 能够在完全不接触凭据本身的情况下使用凭据。如果这一架构要走向更广泛的应用，就需要在能够从多样化的环境中召回上下文的同时，解决上述安全与隐私问题。
9. 结语
回顾整套设计，我们并没有提出全新的理论，而是将计算机系统中经典的工程思想应用到了 Agent 系统的构建中。具体的实现方式会随技术发展而演进，但我们认为背后的系统设计思路有更长期的参考价值。目前，我们基于这套思路和 DeepSeek Harness 构建的内部 Super-agent 实例已经在持续运行，日常参与问题复现与修复、代码审查响应与 DeepSeek Harness 自身的迭代。
正如开篇所述，随着大模型执行单个任务越来越少需要人工干预，限制生产力进一步提升的瓶颈正在转向人的注意力。通过双层架构、事件驱动、异步多信道交互、存算分离与外部 Watchdog，系统在底层接管了繁琐的会话管理与上下文同步，使人类得以从具体的执行细节进一步上移到更高层的决策与验收。
在这种形态下，Agent 不再只是一个被动等待指令的对话窗口，而是演进为数字环境中持续在线的自主协作者：面向个人，它可以是跨设备协助处理日常事务的个人助手；面向团队，它融入研发工作流，承接并推进具体任务。我们相信，随着模型能力与底层系统架构的共同演进，这种更自主的工作方式有望成为人机协作的常态。

登月流程拆解分析
载人登月不是比火箭粗细，是比整条技术链路的可靠性、可持续性，以及背后的工业体系能不能撑住长期的深空探索。
我们把整个任务拆解开，其实就是“两发、一对接、一落一回”，每一步目标都非常明确。
第一枚长征十号先发射，把揽月着陆器送到地月转移轨道，着陆器自己刹车进入环月轨道，在天上待命。这一发不载人，只送硬件，风险独立，就算出问题，也不涉及航天员安全。
第二枚火箭再发射梦舟载人飞船，搭载3名航天员走同样的地月轨道，进入环月后和提前等在那里的着陆器完成交会对接。
对接完成后，2名航天员从飞船转移到着陆器，着陆器分离下降，靠发动机反推减速、悬停避障，最终软着陆在月球预选区域。
剩下1名航天员留在环月轨道的飞船里，值守待命。
月面任务期间，两名航天员出舱开展科学探测、采集样品、布设试验装置，完成任务后回到着陆器的上升段，发动机点火从月面起飞，再次回到环月轨道，和飞船对接，人和样品转移回飞船。
最后着陆器上升段废弃，飞船带着3名航天员点火离开环月轨道，以第二宇宙速度返回地球，再入大气层降落。
这是笔者以自己的理解查找相关资料拆解出来的流程，在技术细节层面或有不尽完善之处。
但对比就会发现，整个流程的核心逻辑，和阿波罗计划是同源的：都是留一艘飞船在环月轨道当“摆渡船”，登月舱单独负责下降和上升，不用把整艘飞船都降到月面，节省燃料和结构重量。
区别只在于，阿波罗用土星五号一次性把飞船+登月舱全打上去，我们分成两次打。
为什么阿波罗是一次，我们是分两次？
原因是，当年土星五号单发登月，是冷战背景下不计成本的政治冲刺——为了赶十年之约，美国硬生生堆出了一款推力空前的火箭，一发就能把近50吨载荷送到环月轨道，视觉冲击力拉满，但代价也同样拉满。

・航天员出舱进行月面作业，

个人售房场景下，税法还是相对宽容的：个人将购买满两年的住房对外销售，免征增值税；个人转让自用达五年以上并且是家庭唯一生活用房的所得，免征个人所得税；土地增值税对个人销售住房长期实行暂免征收的政策。
然而，当房产的产权人从自然人变为基金会，基金会想要再次出售，就得按法人经营主体的规则纳税。
第一，土地增值税为例。
《土地增值税暂行条例》第六条规定，计算增值额的扣除项目包括“取得土地使用权所支付的金额”“开发土地的成本、费用”“新建房及配套设施的成本、费用，或者旧房及建筑物的评估价格”以及“与转让房地产有关的税金”等。
第七条规定土地增值税实行四级超率累进税率，增值额未超过扣除项目金额百分之五十的部分，税率为百分之三十；超过百分之五十至百分之一百的部分，税率为百分之四十；超过百分之一百至百分之二百的部分，税率为百分之五十；超过百分之二百的部分，税率为百分之六十。
对于一套通过遗赠无偿取得的房产，基金会没有“取得土地使用权所支付的金额” ，也没有“旧房及建筑物的评估价格”所对应的历史购置成本可以扣除。
换言之，出售价格中几乎全部构成“增值额”，超率累进税率直接作用于这一整块增值之上，纳税基数被制度性放大。
虽然财税〔2016〕36号附件1第十四条规定，“单位或者个人向其他单位或者个人无偿转让不动产用于公益事业或者以社会公众为对象的，无需视同销售不动产，不缴纳增值税”，这使得老人将房产遗赠给基金会这一取得环节不产生增值税负担，但基金会作为受赠主体再行出售时，仍须就转让行为承担增值税纳税义务，并不因最初取得行为的公益属性而免除。
第二，企业所得税。
《企业所得税法》第二十六条规定了企业的免税收入，其中包括“符合条件的非营利组织的收入”。
但该法及其实施条例同时要求，非营利组织的免税收入限于与该组织非营利活动相关的收入，而转让受赠不动产所得并不自动落入免税范围。

[图片]
AI解码师

PD 分离的依据变弱了。做 PD 分离，是因为 prefill 计算受限、decode 访存受限，两类负载放在一起会互相干扰，分开部署更划算。扩散模型的每一步去噪本身就带有 prefill 的计算特征，“计算受限的 prefill 加访存受限的 decode”这个划分就不太成立了。过去两年不少公司花大力气做的 PD 分离集群，接扩散模型时可能需要重新设计。
调度器多了一个运行时参数：块大小。这一点最值得做 Infra 的同行注意。在块扩散模型里，块大小决定了每次前向处理多少 token，因此直接决定了计算和访存的比例。块大一些，更偏计算受限，单用户更快；块小一些，更接近自回归，适合拉高并发。前面提到的硬件分析论文也给出了类似判断，认为块大小可以作为一个硬件层面的运行参数来调。
这意味着调度器以后除了决定“这个请求放到哪张卡上”，还要决定“这个请求按多大的块来生成”。闲时用大块追求低延迟，高峰时用小块保吞吐，同一个模型可以在两种工作模式之间切换。对调度系统来说，这是全新的问题。
请求耗时更难预测。自回归模型每个 token 的耗时基本稳定，输出长度乘以单 token 耗时就能估出总耗时。扩散模型的去噪步数可以根据置信度提前结束，同样长度的输出，简单内容可能几步就完成，复杂内容要跑满全部步数。SLO 保障、超时策略、负载均衡的权重计算，原来依据的都是“耗时大致和 token 数成正比”这个假设，现在都需要要重新评估。
按 token 计费的逻辑会受影响。如果生成同样 1000 个 token，A 请求用 8 步、B 请求用 64 步，算力消耗差了好几倍，按 token 收一样的价格就不太合理。大概率会有厂商尝试按去噪步数或实际算力计费，或者至少在按 token 定价的基础上分出档位。这件事看起来属于商业层面，但计量系统要从底层采集每个请求的实际计算量，最终还是要落到 Infra 来做。
前面讲了扩散模型的种种不同，这里还有一个点就是：块扩散的块大小设为 1，就等同于自回归。
过去一年里，扩散阵营进展最大的方向都是在往自回归靠拢：Fast-dLLM 补上了 KV Cache，SDAR 和 LLaDA 2.0 采用块内并行、块间顺序生成，还有不少工作直接从已训练好的自回归模型出发，转换成扩散模型。
今年还有一篇叫 HERALD 的论文，研究的是块扩散模型的 KV Cache 怎么卸载到 CPU 内存，原因是块扩散的 KV Cache 同样会随上下文长度线性增长，长上下文下显存一样紧张。

首先，并行生成整个文本块使其速度大幅提升（无需逐词等待）。
